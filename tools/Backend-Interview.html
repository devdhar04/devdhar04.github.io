07 What are Java Streams? What types of operations do they have?
★★★ ▼
Model Answer

A Stream is a pipeline over a data source — it doesn't store data, it processes it lazily. Two categories of operations:

  • Intermediate (lazy, return another Stream): filter, map, flatMap, sorted, distinct, limit
  • Terminal (trigger execution, return a value): collect, forEach, reduce, count, findFirst, anyMatch

Lazy evaluation means: filter(isActive).map(toDto).limit(10) — the limit short-circuits, so only 10 elements go through the full pipeline.

08 When do you use map vs flatMap?
★★★ ▼
The one-sentence rule

map = 1 element in → 1 element out. flatMap = 1 element in → 0 or many elements out, and the inner streams are flattened into one.

// map: one policy → one DTO policies.stream() .map(p -> new PolicyDTO(p.getId(), p.getAmount())) .collect(Collectors.toList()); // flatMap: one agent → many policies (flatten) agents.stream() .flatMap(agent -> agent.getPolicies().stream()) .filter(Policy::isActive) .collect(Collectors.toList());
Interview tip: Give the example immediately — agents with policies is perfect for Manulife's domain.

11 What is CORS?
★★★ ▼
30-second definition

CORS is a browser-enforced policy that blocks a web page from calling an API on a different domain unless the API explicitly allows it via Access-Control-Allow-Origin headers. The browser sends a preflight OPTIONS request first; if the server doesn't respond with the right headers, the browser blocks the actual request — the server never even sees it.

In Spring Boot: @CrossOrigin(origins = "https://portal.manulife.com") or configure it globally in WebMvcConfigurer. Never use * in production.

12 What is CSRF?
★★★ ▼
What went wrong: You confused CSRF with XSS and gave a vague answer. Practice this until it's instant.
Crisp definition

CSRF is when a malicious site uses the victim's browser to make authenticated requests to your site — because the browser automatically sends cookies. The victim doesn't know it's happening.

Classic attack: You're logged into your bank. You visit evil.com. A hidden form there auto-submits to bank.com/transfer?to=hacker&amount=1000. Your browser sends the bank cookie → bank processes it.

Prevention: CSRF tokens (unique per session, sent in header not cookie), SameSite=Strict cookies, or — for REST APIs using JWT in Authorization header (not cookies) — CSRF is not a concern because the token won't be auto-sent.

13 What is XSS (Cross-Site Scripting)?
★★★ ▼
3 types + prevention

XSS = attacker injects malicious script into pages viewed by other users. Three variants:

  • Stored XSS — script saved in DB, served to every user who loads that page. Worst type.
  • Reflected XSS — script is in the URL, reflected back in the response (e.g., error messages showing unsanitised input).
  • DOM XSS — client-side JS writes attacker-controlled data directly to the DOM without sanitisation.

Prevention: Angular auto-escapes by default. For backend: never interpolate raw user input into HTML responses. Use Content-Security-Policy headers. Sanitise all inputs with libraries like OWASP Java HTML Sanitizer.

15 How do you design a microservice to handle 10,000 requests/second?
★★★ ▼

First — ask this before answering:

"Before I design — is this read-heavy, write-heavy, or both? And is consistency strong or eventual? That changes the architecture significantly."

The answer — 7 pillars
  1. Stateless pods: No session state in memory — use Redis for shared state. Enables unlimited horizontal scaling behind the AKS load balancer.
  2. Connection pool tuning: HikariCP pool size = (core count × 2) + disk spindles. With 3 pods × 10 connections = 30 DB connections (within Azure SQL limits).

  6. HPA: Kubernetes Horizontal Pod Autoscaler scales on CPU >70% or custom metric (request queue depth).

16 Design a fund-transfer microservice — both read and write at scale.
★★★ ▼
Chetan's exact scenario: Move funds from account A to account B. Both read AND write. Design it.
The answer — lead with constraints

"For a financial system, I prioritise consistency and atomicity over availability. That means ACID transactions, not eventual consistency for the transfer itself."

  1. ACID transaction: Lock both accounts, debit A, credit B, commit — one database transaction. Rollback on any failure. No eventual consistency for the core transfer.
  2. Idempotency key: Client sends a UUID with every transfer request. Server stores it with the transaction. Duplicate requests return the original result — no double debits.
  3. CQRS split: Writes go to master Azure SQL. Balance reads go to Redis (invalidated on write) then read replica. Reduces DB load for the 90% of traffic that is just checking balances.
  4. Saga pattern for multi-service transfers (e.g., cross-bank): each step publishes an event; compensating transactions handle rollback if a downstream step fails.
  5. Optimistic locking: Version column on accounts table. Concurrent writes to the same account retry if version mismatch — prevents race conditions.
  6. Audit log: Every transaction written to an immutable append-only table with timestamp, user ID, and amounts. Regulatory requirement.
17 How do you implement eventual consistency in Java microservices?
★★★ ▼
What went wrong: You started talking about row-locking (pessimistic concurrency) — which is the opposite of eventual consistency. They're different concepts. Be clear on which is which.
The distinction first

Strong consistency = after a write, all readers see it immediately. Use for: transfers, payments, seat booking.

Eventual consistency = after a write, all nodes will eventually agree, but reads may see stale data temporarily. Use for: notification counters, analytics, read replicas, search indexes.

How to implement eventual consistency
  1. Event-driven: After a write, publish a Kafka event. Downstream services consume it and update their local view. The producer doesn't wait for downstream.
  2. Idempotent consumers: Kafka consumers must handle duplicates — use a dedupe table keyed by event ID. Process once, log the event ID, skip duplicates.
  3. Saga pattern: Long-running distributed transactions. Each step publishes an event → next service acts on it. If a step fails, compensating events undo previous steps.
  4. Outbox pattern: Write to your DB and an outbox table in the same transaction. A separate process polls the outbox and publishes to Kafka. Guarantees no lost events even on app crash.
// Outbox pattern — atomically write + schedule event @Transactional public void transferFunds(TransferRequest req) { accountRepo.debit(req.fromAccount(), req.amount()); accountRepo.credit(req.toAccount(), req.amount()); // In same TX — if this fails, rollback everything outboxRepo.save(new OutboxEvent("TRANSFER_COMPLETED", req)); } // Separate scheduler picks up outbox and publishes to Kafka

19 Concurrent editing: Manager and Agent both edit the same page. Navigating saves the screen data. How do you prevent one from overwriting the other?
★★★ ▼
Chetan's exact scenario
Manager opens an application form. Agent opens the same form. Both are on the same page. Manager fills field ABC = "123". Agent fills ABC = "456". When either navigates away, the page saves. The second save overwrites the first. How do you fix it?
You got the right idea but explained it circuitously. Chetan wanted to hear: "optimistic locking" and "dirty check" — name them explicitly.
Two-part solution — frontend + backend

Frontend — dirty check before save: Compare current form state to the initial loaded state. If unchanged, skip the save API call entirely. This handles the case where the Manager only viewed and didn't edit — no save is triggered.

Backend — optimistic locking: Every application record has a version integer. When the client loads the form, it receives the current version. When it saves, it sends that version back. The DB update is: UPDATE app SET data=? WHERE id=? AND version=?. If version has changed (Agent saved first), zero rows update → return 409 Conflict. Frontend shows: "This record has been modified by another user. Please refresh."

// JPA optimistic locking — one annotation @Entity public class Application { @Version private Long version; // auto-incremented on every write private String data; } // If version mismatch, JPA throws OptimisticLockException // Handle in @ControllerAdvice → return 409 Conflict
Key term to say out loud: "Optimistic locking with a version column" — Chetan is looking for this phrase.
20 Manager/Agent hierarchy: Manager can see Agent's applications. How do you design this access control?
★★★ ▼
Clean answer in 45 seconds

This is attribute-based access control (ABAC) with a manager-subordinate relationship, not just simple RBAC.

  1. Data model: User table has a manager_id FK (self-referencing). An agent's applications are linked to their user_id.
  2. Query filter: The API for "get applications" automatically filters by: if role=AGENT, return only my applications. If role=MANAGER, return applications of users where manager_id = me.
  3. Service layer enforcement: Never let the client pass a filter — derive it server-side from the JWT's user ID and role claims. A manager cannot request applications of agents outside their team.
  4. Audit log: Every read is logged — who accessed whose data, when.

24 How do you troubleshoot a pod that keeps restarting?
★★★ ▼
5-step runbook — say it in order
  1. kubectl describe pod <name> — check Last State and Events. Look for: OOMKilled (memory limit too low), CrashLoopBackOff (app crashing), Liveness probe failed.
  2. kubectl logs <name> --previous — read the logs of the dead container. Usually a stack trace tells you everything.
  3. OOMKilled? → Increase memory limit in deployment YAML (resources.limits.memory). Check for memory leaks with heap dump.
  4. CrashLoopBackOff? → Check if app startup is failing. Common cause: missing env var / secret. Verify all envFrom and secretKeyRef are correct.
  5. Liveness probe failing? → The app is running but the health endpoint isn't responding in time. For slow-starting Spring Boot apps, add a startupProbe with a longer timeout before liveness kicks in.

25 What is a Virtual Service in Kubernetes (Istio)?
★★★ ▼
The one-sentence definition + use cases

A VirtualService in Istio defines traffic routing rules — it tells the service mesh where to send a request and under what conditions.

Use cases:

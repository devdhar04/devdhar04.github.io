Chapter 01

What is AKS?

Start from the very beginning — containers, Kubernetes, then AKS.

📦
Step 1 — What is a Container?
Before Kubernetes, understand containers

A container is a lightweight package that holds your application code + everything it needs to run (Java runtime, dependencies, config). Think of it like a shipping container — standardised box that runs the same everywhere.

You've already used Docker containers in your Spring Boot projects. When you run docker build and docker run, you're creating and running containers.

🚢 Analogy: A container is like a lunchbox. Everything your app needs for the day is packed inside. Doesn't matter if you're at home, office, or a café — the lunchbox works the same.
⚙️
Step 2 — What is Kubernetes?
The container orchestrator — manages thousands of containers

Kubernetes (K8s) is a system that manages containers at scale. Imagine you have 50 containers running your Spring Boot app across 10 servers. Kubernetes handles:

  • Starting and stopping containers
  • Restarting crashed containers automatically
  • Distributing traffic across containers (load balancing)
  • Scaling up/down based on traffic
  • Deploying new versions without downtime
🏭 Analogy: If containers are workers, Kubernetes is the factory manager. It decides how many workers to hire, which shifts they work, replaces sick workers automatically, and ensures production never stops.
☁️
Step 3 — What is AKS?
Azure Kubernetes Service — managed Kubernetes on Microsoft Azure

AKS (Azure Kubernetes Service) is Microsoft Azure's managed version of Kubernetes. Running Kubernetes yourself is hard — you need to set up and maintain the control plane, upgrades, security, networking. AKS does all of that for you.

You get a fully functional Kubernetes cluster with one command. Azure manages the brain of Kubernetes (control plane) for free. You only pay for the worker machines (nodes) that run your apps.

  • Microsoft manages: upgrades, security patches, control plane availability
  • You manage: your application deployments, scaling config, networking rules
🏠 Analogy: Running Kubernetes yourself = buying land and building a house. AKS = renting a fully-managed apartment. The building's infrastructure (plumbing, electricity, security) is handled. You just move in your furniture (your apps).

Kubernetes vs AKS — key difference

AspectPlain Kubernetes (self-managed)AKS (managed)
Control PlaneYou set it up and maintain itAzure manages it (free)
UpgradesYou do them manuallyAzure handles them
AvailabilityYour responsibility99.9% SLA from Azure
IntegrationManual Azure integrationBuilt-in: Azure AD, Key Vault, Monitor
CostPay for all machines incl. control planePay only for worker nodes
Interview one-liner: "AKS is Azure's managed Kubernetes service. Azure handles the control plane, upgrades, and security. We focus on deploying and scaling our applications."
Chapter 02

Core Concepts

The 8 building blocks of Kubernetes. Understand these and everything else makes sense.

🫘
Pod
The smallest unit in Kubernetes

A Pod is the smallest deployable unit in Kubernetes. It wraps one or more containers that share the same network and storage. In practice, most pods contain one container (your Spring Boot app).

Pods are ephemeral — they are created and destroyed frequently. Never depend on a specific pod staying alive. If a pod crashes, Kubernetes creates a new one automatically.

  • Each pod gets its own IP address inside the cluster
  • Pods on the same node share the node's resources (CPU, memory)
  • Pods don't survive node failures — they're rescheduled on another node
💡 Analogy: A Pod is like one instance of your Spring Boot app running in a server. If the server crashes, the app crashes. Kubernetes starts a new one automatically on a healthy server.
🖥️
Node
A virtual machine that runs pods

A Node is a virtual machine (VM) in Azure that runs your pods. In AKS, nodes are Azure VMs (like Standard_D4s_v3). Each node runs a Kubernetes agent (kubelet) that manages pods on that node.

  • You pick the node size (CPU, memory) when creating your AKS cluster
  • Multiple pods run on each node
  • Nodes are grouped into Node Pools in AKS
🏗️ Analogy: A Node is the physical server (or VM). Pods are apps running on that server. One server can run many apps.
🚀
Deployment
Manages how many pods run and how they update

A Deployment tells Kubernetes: "I want 3 replicas of my Spring Boot app running at all times, using image version 2.1". Kubernetes maintains that state — if a pod dies, it creates a new one.

Deployments also handle rolling updates — when you deploy a new version, Kubernetes starts new pods with the new version before killing old ones. Zero downtime.

  • replicas: 3 — run 3 pods
  • image: myapp:2.1 — which container image to use
  • strategy: RollingUpdate — update pods one at a time
👔 Analogy: A Deployment is like an HR policy: "We always have 3 customer service agents on shift. If one calls in sick, hire a replacement immediately."
🔗
Service
A stable network endpoint for your pods

Pods come and go with different IP addresses. A Service is a stable virtual IP that sits in front of your pods and load-balances traffic to them. Other apps don't talk to pods directly — they talk to the Service.

Three main types:

  • ClusterIP — only accessible inside the cluster (default)
  • NodePort — exposed on each node's IP on a specific port
  • LoadBalancer — creates an Azure Load Balancer with a public IP
☎️ Analogy: A Service is like a company's main phone number. Employees (pods) come and go, but customers always call the same number. The receptionist (Service) routes the call to an available employee.
🗺️
Ingress
HTTP routing from the internet into your cluster

An Ingress is a set of rules for routing external HTTP/HTTPS traffic to the right Service. One Ingress can route multiple domain paths to different services.

  • api.company.com/users → user-service
  • api.company.com/orders → order-service

An Ingress Controller (e.g., NGINX, Azure Application Gateway) is the actual software that implements the rules.

🗄️
ConfigMap & Secret
Configuration and sensitive data for pods

ConfigMap — stores non-sensitive configuration as key-value pairs. Mounted into pods as environment variables or files.

Secret — stores sensitive data (passwords, API keys, connection strings) in base64-encoded form. In AKS, you connect Secrets to Azure Key Vault for true security.

🔑 Analogy: ConfigMap = a sticky note with app settings. Secret = a locked safe with passwords. Both are handed to the app when it starts.
📁
Namespace
Logical isolation inside a cluster

A Namespace divides a cluster into virtual sub-clusters. Used to separate environments (dev/staging/prod) or teams within the same physical cluster.

  • Default namespace: default
  • You create: namespace: production, namespace: staging
  • Resource quotas can be set per namespace

Chapter 03

AKS Architecture

How the pieces fit together — Control Plane, Worker Nodes, and Azure integrations.

The two halves of a Kubernetes cluster

Control Plane (Azure manages)

  • API Server — entry point for all kubectl commands
  • etcd — database storing all cluster state
  • Scheduler — decides which node a new pod goes to
  • Controller Manager — ensures desired state is maintained

Worker Nodes (you manage)

  • kubelet — agent on each node, talks to Control Plane
  • kube-proxy — handles network rules on the node
  • Container runtime — actually runs containers (containerd)
  • Your pods — your Spring Boot apps run here
Interview tip: "In AKS, Azure manages the control plane completely — we don't pay for it or maintain it. We only manage the worker nodes where our applications run. This is the biggest operational advantage of AKS over self-managed Kubernetes."
Chapter 04

YAML & Configuration

Everything in Kubernetes is defined in YAML files. Learn to read and write them.

Deployment YAML — your Spring Boot app

This is what you write to deploy your Spring Boot API to AKS

  deployment.yaml — Spring Boot API
apiVersion: apps/v1
kind: Deployment
metadata:
  name: policy-api                    # name of this deployment
  namespace: production               # which namespace
spec:
  replicas: 3                         # run 3 pods at all times
  selector:
    matchLabels:
      app: policy-api                 # which pods this deployment manages
  template:
    metadata:
      labels:
        app: policy-api
    spec:
      containers:
      - name: policy-api
        image: myregistry.azurecr.io/policy-api:2.1.0   # container image
        ports:
        - containerPort: 8080
        
        # Environment variables from ConfigMap and Secret
        env:
        - name: SPRING_PROFILES_ACTIVE
          value: "production"
        - name: DB_URL
          valueFrom:
            secretKeyRef:             # pulled from Azure Key Vault Secret
              name: db-credentials
              key: url
        
        # Resource limits — CRITICAL for AKS
        resources:
          requests:                   # minimum guaranteed
            memory: "512Mi"
            cpu: "250m"
          limits:                     # maximum allowed
            memory: "1Gi"
            cpu: "500m"
        
        # Health probes
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 20
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 15

Service YAML — expose your deployment

  service.yaml
apiVersion: v1
kind: Service
metadata:
  name: policy-api-service
  namespace: production
spec:
  selector:
    app: policy-api               # routes to pods with this label
  ports:
  - protocol: TCP
    port: 80                      # service port (external)
    targetPort: 8080              # pod port (internal)
  type: ClusterIP                 # internal only — Ingress handles external

Resource requests vs limits — important distinction

SettingWhat it meansConsequence if violated
requests.memoryMinimum memory guaranteed to this podPod won't start if node can't provide it
limits.memoryMaximum memory the pod can usePod is killed with OOMKilled if exceeded
requests.cpuMinimum CPU guaranteedPod may be scheduled on different node
limits.cpuMaximum CPU the pod can usePod is throttled (slowed down, not killed)
Common interview question: "What is OOMKilled?" — It means Out Of Memory Killed. The pod exceeded its memory limit and Kubernetes killed it. You'll see this in kubectl describe pod. Fix: increase the memory limit.

CPU units explained

250m = 250 millicores = 0.25 CPU cores. 1000m = 1 full CPU core.

So requests.cpu: 250m means "guarantee this pod at least ¼ of a CPU core".

Istio — Virtual Service & Destination Rule

These are what Chetan asked. Istio is a service mesh layer on top of Kubernetes.

🗺️
Virtual Service
Traffic routing rules — WHERE traffic goes

A VirtualService defines routing rules within Istio's service mesh. It answers: which version of a service should receive this request?

  • Canary deploy: 90% of traffic → v1, 10% → v2 (new version being tested)
  • A/B testing: Users with header X-Beta: true → v2, everyone else → v1
  • Fault injection: Simulate 5% errors for chaos testing
  • Retries: Auto-retry failed requests up to 3 times
🗺️ Analogy: VirtualService is the GPS navigation — it decides the route. "Take 90% of traffic on the main road (v1), and 10% on the new road being tested (v2)."
  virtual-service.yaml — canary deployment
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: policy-api-vs
spec:
  hosts:
  - policy-api
  http:
  - route:
    - destination:
        host: policy-api
        subset: v1              # 90% to stable version
      weight: 90
    - destination:
        host: policy-api
        subset: v2              # 10% to new version (canary)
      weight: 10
🚦
Destination Rule
Traffic behaviour — HOW traffic behaves at the destination

A DestinationRule defines policies that apply once traffic reaches its destination. It answers: how should we handle traffic once it arrives?

  • Load balancing algorithm: ROUND_ROBIN, LEAST_CONN, RANDOM
  • Circuit breaker: Eject a pod from the load balancer after 5 consecutive failures for 30 seconds
  • Connection pool: Max 100 concurrent connections per pod
  • Subsets: Define v1 and v2 pods by their labels (used by VirtualService)
🚦 Analogy: DestinationRule is the traffic management system once you're at the destination — speed limits, lane rules, which exits are closed. VirtualService decides your route; DestinationRule manages what happens when you arrive.
  destination-rule.yaml
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: policy-api-dr
spec:
  host: policy-api
  trafficPolicy:
    loadBalancer:
      simple: ROUND_ROBIN         # distribute evenly across pods
    outlierDetection:             # circuit breaker
      consecutive5xxErrors: 5     # eject after 5 consecutive errors
      interval: 30s               # check every 30 seconds
      baseEjectionTime: 30s       # eject for 30 seconds
  subsets:
  - name: v1
    labels:
      version: v1                 # pods labelled version=v1
  - name: v2
    labels:
      version: v2                 # pods labelled version=v2
The one-line distinction to memorise: VirtualService = the map (routing rules, which version gets traffic). DestinationRule = the road rules (how traffic behaves: load balancing, circuit breakers, connection limits).
Chapter 06

Scaling & Health

How Kubernetes keeps your app alive and scales it automatically.

Health Probes — how Kubernetes knows if your pod is healthy

💚
Readiness Probe
Is this pod ready to receive traffic?

The readiness probe checks if your pod is ready to serve requests. If it fails, Kubernetes removes the pod from the Service's load balancer — no traffic is sent to it — but the pod keeps running.

Use case: Spring Boot takes 20 seconds to start. Without a readiness probe, Kubernetes sends traffic immediately and users get errors. With it, traffic only routes to the pod after startup is complete.

🏪 Analogy: A restaurant that's open but the kitchen isn't ready yet. The "Open" sign is off (not in load balancer) until the kitchen is ready. Then the sign turns on.
❤️
Liveness Probe
Is this pod still alive? Should we restart it?

The liveness probe checks if your pod is healthy during its life. If it fails, Kubernetes restarts the pod. Used to detect when an app has deadlocked or entered a bad state from which it can't recover.

Use case: Your Spring Boot app is running but has a deadlocked thread — it's responsive to the health endpoint? No. Kubernetes restarts it.

🚀
Startup Probe
Give slow-starting apps time to boot

The startup probe runs before liveness and readiness probes kick in. It gives slow-starting apps (like Spring Boot with many beans) extra time to boot without the liveness probe killing them prematurely.

Rule: If your app takes more than 30 seconds to start, use a startup probe.

  probes in deployment.yaml
        startupProbe:                       # runs first, gives app time to boot
          httpGet:
            path: /actuator/health
            port: 8080
          failureThreshold: 30              # 30 × 10s = 5 minutes to start
          periodSeconds: 10

        readinessProbe:                     # is it ready for traffic?
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 0           # starts after startupProbe succeeds
          periodSeconds: 10
          failureThreshold: 3

        livenessProbe:                      # is it still healthy?
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          periodSeconds: 15
          failureThreshold: 3              # restart after 3 consecutive failures

HPA — Horizontal Pod Autoscaler

📈
Horizontal Pod Autoscaler (HPA)
Automatically scales pod count based on load

HPA watches your pod's CPU/memory usage and automatically adds or removes pods to maintain target utilisation. You set: min pods, max pods, and target CPU%.

Example: Normal traffic = 3 pods at 30% CPU. Traffic spike = HPA scales to 8 pods to keep each at ~70% CPU. Spike ends = HPA scales back to 3.

🚖 Analogy: Like Uber surge pricing — when demand spikes, more drivers (pods) come online automatically. When it's quiet, fewer drivers are needed.
  hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: policy-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: policy-api
  minReplicas: 3                  # never go below 3 pods
  maxReplicas: 10                 # never exceed 10 pods
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70    # scale up when average CPU > 70%

Chapter 07 · 40 Questions

Interview Q&A

Every question an interviewer is likely to ask a backend engineer about AKS. Click to reveal model answers. Mark as mastered when you can answer without reading.

Fundamentals

EASY What is AKS and why would you use it over running Kubernetes yourself?
▼
Model Answer

AKS is Azure's managed Kubernetes service. Azure manages the control plane — the API server, etcd, scheduler, controller manager — for free. We only pay for and manage the worker nodes where our applications run.

The advantages over self-managed Kubernetes: no operational overhead for control plane upgrades and patches, built-in integration with Azure AD, Key Vault, Monitor, and Container Registry, and a 99.9% SLA on the control plane. For a backend team, this means we focus on deploying applications rather than maintaining Kubernetes infrastructure.

EASY What is a Pod? How is it different from a container?
▼
Model Answer

A container is the runtime instance of a Docker image — it's one isolated process. A Pod is Kubernetes' abstraction that wraps one or more containers that share the same network namespace and storage volumes.

In practice, most pods contain a single container — your Spring Boot app. The pod is the smallest deployable unit in Kubernetes. Pods are ephemeral: when they die, Kubernetes creates new ones. You never interact with individual containers in Kubernetes — you work with pods.

EASY What is a Deployment and what does it guarantee?
▼
Model Answer

A Deployment is a Kubernetes resource that declares the desired state for your pods — which container image to run, how many replicas, resource limits, and health probes. Kubernetes' controller continuously reconciles the actual state with the desired state.

It guarantees: if a pod crashes, a new one is created. If a node goes down, pods are rescheduled on healthy nodes. It also manages rolling updates — deploying new image versions without downtime by starting new pods before terminating old ones.

EASY What is the difference between ClusterIP, NodePort, and LoadBalancer services?
▼
Model Answer

ClusterIP — only accessible inside the cluster. Used for internal service-to-service communication. For example, my policy-api calling the claims-service internally.

NodePort — exposes the service on a static port on every node. Accessible from outside the cluster at NodeIP:NodePort. Only used for testing — not production.

LoadBalancer — provisions an Azure Load Balancer with a public IP. Used when you need direct external access without an Ingress. More expensive as each service gets its own public IP. In production we prefer Ingress to share one load balancer across services.

MEDIUM What is a Namespace and why do you use them?
▼
Model Answer

Namespaces provide logical isolation within a single cluster. We use them to separate environments — production, staging, and development all running in the same AKS cluster but completely isolated. Resource quotas can be set per namespace to prevent one environment from consuming all cluster resources.

In practice: kubectl get pods -n production vs kubectl get pods -n staging. Services in different namespaces don't conflict even if they have the same name.

Health Probes

MEDIUM What is the difference between readiness and liveness probes?
▼
Model Answer

Readiness probe — answers "is this pod ready to receive traffic?" If it fails, the pod is removed from the Service's load balancer but keeps running. Used to handle slow startup — Spring Boot takes 20-30 seconds to initialise, so we don't want traffic routed to it immediately.

Liveness probe — answers "is this pod still healthy?" If it fails, Kubernetes restarts the pod. Used to recover from deadlocks or unrecoverable error states where the app is running but can't serve requests.

Key distinction: readiness failure = remove from load balancer. Liveness failure = restart the pod.

MEDIUM What is a startup probe and when do you need one?
▼
Model Answer

A startup probe runs before liveness and readiness probes and gives slow-starting applications time to initialise. While the startup probe is running, liveness and readiness probes are disabled.

We need it when a Spring Boot application takes more than 30 seconds to start — for example, if it loads a large dataset at startup or has many beans to initialise. Without a startup probe, the liveness probe would kill the pod before it finishes starting, causing a restart loop. With failureThreshold: 30 and periodSeconds: 10, the app has up to 5 minutes to start.

MEDIUM What are resource requests and limits? What happens if a pod exceeds its memory limit?
▼
Model Answer

Requests are the minimum resources guaranteed to the pod — used by the scheduler to decide which node can host the pod. Limits are the maximum resources the pod can use.

If a pod exceeds its memory limit, Kubernetes kills it immediately with an OOMKilled (Out Of Memory Killed) status — visible in kubectl describe pod. The fix is to increase the memory limit or fix a memory leak in the application.

If a pod exceeds its CPU limit, it's throttled — slowed down but not killed. CPU limits are softer constraints than memory limits.

Networking & Ingress

MEDIUM How is a service deployed on AKS accessed from outside the cluster?
▼
Model Answer

External traffic flows: Client → DNS (resolves to App Gateway IP) → Azure Application Gateway (TLS termination, WAF, routing rules) → AKS Ingress Controller (NGINX or AGIC) → Kubernetes Service (ClusterIP, load balances across pods) → Pod.

The Application Gateway is the public entry point. It terminates HTTPS (using certificates from Azure Key Vault), applies WAF rules, and routes traffic by hostname or path to the appropriate AKS service. The Ingress Controller inside the cluster maps those paths to internal Services. Services load-balance across the healthy pods.

MEDIUM What is an Ingress and why use it instead of a LoadBalancer service for every microservice?
▼
Model Answer

An Ingress is an HTTP routing layer that consolidates external access through a single entry point. One Ingress can route traffic to dozens of services based on path or hostname — /api/policies → policy-service, /api/claims → claims-service — all sharing one IP address and one load balancer.

Using LoadBalancer for every service means each gets its own Azure Load Balancer and public IP — expensive and unmanageable at scale. An Ingress with path-based routing is cheaper, centralised, and easier to secure (one TLS certificate, one WAF policy).

HARD What is a VirtualService in Istio and what are its use cases?
▼
Model Answer

A VirtualService is an Istio resource that defines traffic routing rules within the service mesh. It answers "which version or subset of a service should receive this request and under what conditions?"

Key use cases: Canary deployments — route 90% to v1 and 10% to v2, gradually shifting traffic as confidence grows. A/B testing — route users with a specific header to a different version. Fault injection — inject artificial delays or errors to test resilience. Retries and timeouts — automatically retry failed requests without changing application code.

HARD What is a DestinationRule and how does it differ from a VirtualService?
▼
Model Answer

VirtualService defines routing rules — where traffic goes and under what conditions. DestinationRule defines traffic policies — how traffic behaves once it reaches its destination.

DestinationRule controls: load balancing algorithm (ROUND_ROBIN, LEAST_CONN), connection pool limits (max concurrent connections per pod), and circuit breaking (eject a pod from the load balancer after N consecutive failures). It also defines subsets — labelling pods as v1 or v2 — which VirtualService references for weighted routing.

Memory hook: VirtualService is the map (route). DestinationRule is the road rules (speed limits, circuit breakers, lane control).

Scaling & Deployments

MEDIUM What is HPA and how does it work?
▼
Model Answer

HPA — Horizontal Pod Autoscaler — automatically scales the number of pod replicas based on observed metrics. You configure a minimum replicas, maximum replicas, and a target metric (typically CPU utilisation at 70%).

Every 15 seconds, the HPA controller checks the current CPU across all pods. If average CPU exceeds 70%, it calculates the number of pods needed to bring it back to 70% and creates them. When load drops, it scales down — but slowly, to avoid flapping.

This pairs with resource requests — HPA uses the requests value as the baseline for utilisation calculations. If requests.cpu is 250m and the pod uses 200m, utilisation is 80%.

MEDIUM What is a rolling update and how does Kubernetes achieve zero-downtime deployments?
▼
Model Answer

A rolling update replaces pods gradually — it starts new pods with the new image version before terminating old ones, ensuring there are always enough pods serving traffic throughout the deployment.

Configured by maxSurge (how many extra pods can exist during update) and maxUnavailable (how many pods can be down during update). With maxSurge: 1 and maxUnavailable: 0, Kubernetes starts one new pod, waits for its readiness probe to pass, then terminates one old pod — repeating until all pods are updated. Zero downtime because there are always healthy pods receiving traffic.

MEDIUM How do you do a canary deployment in AKS without Istio?
▼
Model Answer

Without Istio, you can do a basic canary by running two Deployments — one for v1 with 9 replicas and one for v2 with 1 replica, both with the same label selector. The Service routes to both, giving approximately 90/10 traffic split by pod count ratio.

For more precise traffic splitting (exact percentages, header-based routing), you need Istio's VirtualService or an Ingress controller that supports traffic splitting (like NGINX with split annotations). The Istio approach is more production-grade as it doesn't require matching replica ratios to achieve your desired split.

Troubleshooting

MEDIUM A pod keeps restarting. Walk me through your debugging process.
▼
Model Answer — say this in order

Step 1: kubectl describe pod <name> — check the Last State reason. OOMKilled means memory limit exceeded. CrashLoopBackOff means the app crashes on startup.

Step 2: kubectl logs <name> --previous — read logs from the container before it crashed. Usually a stack trace tells you exactly what failed.

Step 3 — if OOMKilled: Increase resources.limits.memory in the deployment YAML. Check for memory leaks.

Step 4 — if CrashLoopBackOff: App failing at startup. Check all environment variables and secrets are correctly mounted. A missing DB connection string is the most common cause.

Step 5 — if liveness probe failing: App is running but health endpoint not responding. For slow apps, add a startupProbe with failureThreshold: 30.

MEDIUM What is CrashLoopBackOff and what causes it?
▼
Model Answer

CrashLoopBackOff means the container keeps crashing and Kubernetes keeps restarting it, but adds increasing delays (backoff) between restarts — 10s, 20s, 40s, up to 5 minutes — to prevent thrashing the node.

Common causes: missing required environment variable (app crashes because DB_URL is null), wrong container image or image that doesn't exist, out-of-memory on startup (increase memory limit), application bug that throws an exception before the app is ready, or wrong startup command in the Docker image. Always check kubectl logs --previous first.

HARD How do you do a zero-downtime deployment for a Spring Boot app in AKS?
▼
Model Answer

Several things must be in place together:

1. Rolling update strategy with maxUnavailable: 0 — no pod is terminated until a new one is ready.

2. Readiness probe — new pods only receive traffic after the readiness probe passes. Without this, rolling update would send traffic to pods still initialising.

3. Graceful shutdown — configure Spring Boot with server.shutdown=graceful so in-flight requests complete before the pod terminates. Set terminationGracePeriodSeconds: 30 in the pod spec.

4. preStop hook — add a short sleep (5s) in the preStop lifecycle hook so the load balancer has time to stop routing new traffic before Spring Boot starts shutting down.

Security & Config

MEDIUM How do you manage secrets in AKS? How do you avoid hardcoding passwords?
▼
Model Answer

In AKS we use the Azure Key Vault provider for Secrets Store CSI Driver. Secrets are stored in Azure Key Vault (not in Kubernetes YAML or etcd). The AKS pod's managed identity is granted read access to Key Vault. When the pod starts, the CSI driver mounts the secrets as environment variables or files — the pod gets the secret value without it ever appearing in YAML or code.

We never commit secrets to git. Kubernetes native Secrets are base64-encoded (not encrypted) and stored in etcd — they're not secure by default. Azure Key Vault with managed identity is the production approach.

MEDIUM What is a ConfigMap and when would you use it vs an environment variable directly in the deployment?
▼
Model Answer

A ConfigMap stores non-sensitive configuration data as key-value pairs, decoupled from the pod spec. Use it when the same config value is needed across multiple deployments, or when the config changes independently of the app image.

Direct env vars in deployment YAML are fine for single-use, rarely-changing values. ConfigMaps are better for: shared config (multiple services reading the same DB host), config that ops teams change without touching deployment YAML, and mounting config files into pods (e.g., an application.properties file).

Advanced Topics

HARD What is the difference between a Node Pool and a Cluster in AKS?
▼
Model Answer

A Cluster is the entire AKS environment — control plane + all worker nodes. A Node Pool is a group of nodes within a cluster that all have the same VM size and configuration.

You use multiple node pools when different workloads need different VM types. Example: a system node pool with Standard_D4s for general services, and a GPU node pool with NC6 VMs for ML inference workloads. Pods use node selectors or taints/tolerations to target specific pools. This way, expensive GPU nodes only run GPU workloads — not regular Spring Boot apps.

HARD What is a PersistentVolume and when does a backend service need one?
▼
Model Answer

A PersistentVolume (PV) is storage that persists beyond the life of a pod. Pods are ephemeral — when they die, any local storage is lost. PVs survive pod restarts and rescheduling.

Most backend Spring Boot APIs are stateless — they don't need PVs because state lives in Azure SQL or Redis. You need PVs for stateful workloads: databases running in Kubernetes (PostgreSQL, MongoDB), file storage services that store uploaded documents, or services that need a writable filesystem that survives restarts. In AKS, PVs are backed by Azure Disk or Azure Files.

HARD How does Kubernetes decide which node to schedule a pod on?
▼
Model Answer

The scheduler filters nodes first (removes nodes that can't run the pod) then scores remaining nodes and picks the highest scorer.

Filtering: node must have enough CPU and memory to satisfy the pod's requests, node must not have a taint the pod doesn't tolerate, node must match any nodeSelector or affinity rules the pod specifies.

Scoring: prefers nodes that spread the deployment's pods across different nodes (anti-affinity), prefers nodes with the most available resources. The highest-scoring node wins. This is why resource requests are critical — if you don't set them, the scheduler has no information to make a good decision.

HARD What is a DaemonSet? When would you use one vs a Deployment?
▼
Model Answer

A DaemonSet ensures exactly one pod runs on every node (or every node matching a selector). When a new node joins the cluster, the DaemonSet automatically starts a pod on it. When a node is removed, the pod is garbage collected.

Use DaemonSets for node-level infrastructure: log collectors (Fluentd, Filebeat) that need to run on every node to collect logs, monitoring agents (Datadog, Prometheus node-exporter), network plugins. Use Deployments for your application services where you control replica count and don't care which specific nodes they run on.

HARD How does Kubernetes handle service discovery? How does service-A call service-B internally?
▼
Model Answer

Kubernetes uses DNS-based service discovery. Every Service gets a DNS entry automatically: service-name.namespace.svc.cluster.local. Pods within the cluster can call services by name.

When policy-api calls claims-service in the same namespace: http://claims-service:80/claims. Kubernetes DNS resolves this to the ClusterIP of the claims-service. The kube-proxy on the node then load-balances across the healthy pods behind that service using iptables rules.

The application doesn't know about individual pod IPs — it only knows the service name. This is why Services are essential for internal communication.

MEDIUM What is the Cluster Autoscaler and how does it differ from HPA?
▼
Model Answer

HPA scales pods (horizontal scaling of your application). Cluster Autoscaler scales nodes (adds or removes VMs from the node pool).

They work together: HPA sees high CPU, wants to add 3 more pods. But all nodes are full — no room. Cluster Autoscaler detects pending pods that can't be scheduled, provisions a new node from Azure, and the scheduler places the pods there. When load drops, HPA removes pods, nodes become underutilised, and Cluster Autoscaler terminates unneeded nodes to save cost.

MEDIUM What is a StatefulSet and when would you use it?
▼
Model Answer

A StatefulSet is like a Deployment but for stateful applications. Unlike Deployments where pods are interchangeable, StatefulSet pods have stable, unique identities (pod-0, pod-1, pod-2) and stable network names that persist across restarts. Each pod gets its own PersistentVolume.

Use StatefulSets for databases or distributed systems running inside Kubernetes — Cassandra, Kafka, Redis Cluster, Zookeeper — where each instance has a unique role or data partition. For most backend Spring Boot services, use Deployments. If you're using Azure SQL or Azure Redis externally, you don't need StatefulSets at all.

MEDIUM What kubectl commands do you use most in day-to-day work?
▼
Model Answer — give these confidently

kubectl get pods -n production — see all running pods and their status

kubectl describe pod <name> — detailed info, events, restart reasons

kubectl logs <name> --previous — logs from a crashed container

kubectl logs <name> -f — stream live logs

kubectl rollout status deployment/policy-api — watch a deployment roll out

kubectl rollout undo deployment/policy-api — roll back to previous version

kubectl scale deployment/policy-api --replicas=5 — manually scale

kubectl exec -it <pod> -- /bin/sh — shell into a running pod for debugging

kubectl apply -f deployment.yaml — apply a YAML config change

HARD What is a taint and toleration in Kubernetes?
▼
Model Answer

Taints are applied to nodes to repel pods. Tolerations are applied to pods to allow them onto tainted nodes. Together they control which pods can run on which nodes.

Example: a GPU node pool is tainted with gpu=true:NoSchedule. Regular pods can't be scheduled there because they don't tolerate this taint. Only ML inference pods that have the matching toleration can run on GPU nodes. This ensures expensive GPU nodes aren't wasted on regular Spring Boot apps.

MEDIUM What is a Job and a CronJob in Kubernetes?
▼
Model Answer

A Job runs a pod to completion — it starts a pod, waits for it to finish successfully, and then it's done. Used for batch processing, database migrations (run once on deploy), or data import tasks. If the pod fails, the Job retries it.

A CronJob is a Job that runs on a schedule — like a cron expression. Used for: nightly report generation, scheduled cache warming, periodic data cleanup, sending scheduled emails. The cron expression 0 2 * * * runs at 2am every day.

EASY In one sentence — what is AKS?
▼
Model Answer

AKS is Azure's managed Kubernetes service — Azure manages the control plane for free, and we pay only for the worker nodes that run our applications.

EASY What's the difference between a Pod and a Deployment?
▼
Model Answer

A Pod is one running instance of your app — ephemeral, it can die at any time. A Deployment manages pods: it declares how many should run, which image to use, and ensures that desired count is maintained. If a pod dies, the Deployment creates a new one automatically.

MEDIUM Readiness probe vs liveness probe — what's the difference?
▼
Model Answer

Readiness = is this pod ready for traffic? Failure removes it from the load balancer. Liveness = is this pod still healthy? Failure restarts the pod. Readiness handles slow startup. Liveness handles deadlocks and unrecoverable states.

MEDIUM How does traffic from the internet reach your Spring Boot pod in AKS?
▼
Model Answer

Internet → DNS resolves to Azure Application Gateway → App Gateway does TLS termination and routes by path → AKS Ingress Controller routes to the correct Kubernetes Service → Service load-balances to healthy pods → your Spring Boot pod at port 8080.

MEDIUM What is OOMKilled and how do you fix it?
▼
Model Answer

OOMKilled means Out Of Memory Killed — the pod exceeded its memory limit and Kubernetes terminated it. Fix: increase resources.limits.memory in the deployment YAML. Then investigate whether the app has a memory leak using heap dumps or Application Insights memory metrics.

MEDIUM What is HPA and what does it need to work correctly?
▼
Model Answer

HPA automatically scales pod count based on metrics — typically CPU utilisation. It needs: resource requests set on pods (otherwise it can't calculate utilisation), a metrics server running in the cluster, and min/max replica bounds configured. When average CPU across pods exceeds the target%, it adds pods. When it drops, it removes them.

HARD VirtualService vs DestinationRule — explain the difference in one sentence each.
▼
Model Answer

VirtualService defines routing rules — which version of a service gets traffic and under what conditions (canary, A/B, header matching). DestinationRule defines traffic policies at the destination — load balancing algorithm, circuit breaker settings, connection pool limits.

MEDIUM A pod is in CrashLoopBackOff. What are your first 3 commands?
▼
Model Answer

1) kubectl describe pod <name> — check Events and Last State reason. 2) kubectl logs <name> --previous — read the crash log from the dead container. 3) Based on the error: increase memory limit if OOMKilled, fix missing env vars if startup exception, add startupProbe if slow startup killing liveness.

MEDIUM How do you manage secrets in AKS without hardcoding them in YAML?
▼
Model Answer

We store secrets in Azure Key Vault and use the Secrets Store CSI Driver to mount them into pods at runtime. The pod's managed identity has read access to Key Vault. Secrets appear as environment variables in the pod without ever appearing in YAML or being committed to git. This is far more secure than Kubernetes native Secrets which are just base64-encoded in etcd.

HARD How do you achieve zero-downtime deployments in AKS for a Spring Boot app?
▼
Model Answer
